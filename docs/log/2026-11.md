## 2026-11-02: reclaim decided: delete everything on a typed sentence, move Linux into the space (R41, V15)

The question first. With no file copy (decided earlier the same session),
the kept Windows partition is the only place the person's files live, and
reclaim as designed deletes it. Four options were put to the owner:
reclaim refuses while the folders are there; delete only Windows' system
files and keep a data partition; delete everything after a typed sentence;
or wait for the file copy and stop promising reclaim on screen. The
recommendation was to wait. **The owner chose the typed sentence.**

Then a fact found in the code. The keep-Windows install puts Linux in plain
ext4 partitions after the shrunk Windows (`upgrade_/linux/installer/src/verify.rs`,
the storage section). Deleting Windows frees space in front of Linux, and
ext4 grows only at its end. Three options: a new empty partition mounted
in the person's home, move Linux to the front, or leave the space empty.
The recommendation was the new partition (nothing of Linux moves). **The
owner chose to move Linux,** knowing it is a long copy of every block and
that a power cut in the middle can harm the new Linux too.

What follows from it, written into R41: the move runs from the kit stick
(a mounted system cannot be moved); its progress is recorded off the disk
being moved and it resumes after a power cut, which is safe only while the
shift is at least one chunk; shim sits at `EFI/Microsoft/Boot/bootmgfw.efi`
on the Aspire (R21), so `EFI/Microsoft` can never be deleted wholesale; and
the drive-health refusal holds, so the Aspire's row can only be a refusal.
`outcome.json` already records the Windows partition's GUID
(`/windows/partition/guid`), which reclaim matches exactly.

New: R41 (critical, planned), V15 (planned), `r41-reclaim.csv` (header
only). Owed: the sentence's words (ROADMAP, decisions owed), the judging
half and the move on disk images, the rig, a healthy-drive machine.

## 2026-11-06: reclaim built whole: the arm, the run from the stick, the grow, the entries (R41, V15)

settle-in 0.9.0. Built, tested on disk images, never run on the rig or a
machine. What 0.8.0 left owed is now code:

- **The window** (`settle-in-window --reclaim`, "Free up Windows' space"
  in the app menu, placed by settle-in's first start on the keep-Windows
  path only, so the installer and its frozen golden stay as they were).
  Its pages: what reclaim does; `reclaim check` (root, through pkexec),
  which mounts Windows read-only with ntfs-3g, makes the plan and names the
  folders that will be lost, or every refusal; the typed sentence; then the
  last page. Its one button, "Restart now", runs `reclaim arm` and restarts
  at once. The arm is inside that click on purpose. An armed computer the
  person had not clicked for could delete Windows at any later restart,
  which rule #3 forbids.
- **The arm** writes nothing on the internal disk: the plan again, the
  kit stick checked (the same job id, on USB, not the disk Linux is on, a
  kit new enough to have `ks-reclaim.cfg` and the GRUB branch), an order
  with the whole table onto the stick, the marker, a one-time start.
- **The stick**: a new GRUB branch on converted sticks only, and
  `ks-reclaim.cfg`, a kickstart with no storage, image or packages
  (`make-kit.sh` refuses one that has them). Its `%pre` is `settle-in
  reclaim run`. Before anything is written: the disk found by its GPT id
  (never the stick), its table equal to the order's, the plan made again
  and equal to the agreed one, nothing on the disk mounted or used as swap,
  both file systems ext4 and clean (`e2fsck -n`), a GRUB file to stub. A
  refusal removes the marker and the entry and starts Linux untouched.
- **After the commit**, each step journaled on the stick in two alternating
  files: the ESP's `grub.cfg` files stubbed and the stick first in the
  firmware's order (a half-moved Linux never starts, and a power cut comes
  back to the stick); the move; the table; `e2fsck -f -y`, `resize2fs` and
  `e2fsck -n`; the finish. The finish puts the `grub.cfg` files back,
  removes GRUB's 'Windows (kept)' entry, restores the firmware's order
  without the stick, and removes Windows' boot files and entries only when
  Linux does not start through them. When shim sits in Windows' slot, as on
  the Aspire (R21, R22), only Windows' own kept loader goes.
- After each sync the disk's cache is dropped (`BLKFLSBUF`), so the hash
  after the move reads the drive, not the kernel's memory of it.

An independent review of the writer found ten defects before anything
ran. All were fixed the same day; each could have destroyed data or left
the computer unable to start:

1. A resumed run did no checks. Now every step first reads the disk's
   table and stops unless it is the one this run left; every resume checks
   that nothing uses the disk; and `reclaim run` refuses unless the kernel
   was started with `upg.mode=reclaim` (polkit's `reclaim` action would
   otherwise have reached it from a running Linux).
2. The guard stubbed Linux's start files before the stick was first in the
   order. Now the order is written and read back first, and the stick's
   entry and a readable order are checked before the commit.
3. The finish decided again what of Windows' startup to delete, so a second
   pass could take shim's folder on the Aspire. Now the guard decides once,
   journals it, and the finish only follows it. Windows' slot counts as
   Windows' own only when its bytes equal the ESP snapshot `%pre` took
   before the install, and its folder goes only when this Linux started
   from an entry of its own (`BootCurrent`, read at the arm).
4. Windows could still start while C: was being overwritten. Its own
   loader is now held aside and its entries kept out of the order during
   the run.
5. A cut while `/boot/grub2/grub.cfg` was rewritten could leave it empty.
   The original is saved on the stick first, and every pass works from it.
6. The firmware's order was put back before the finish's last steps. It is
   now the last step.
7. A Linux entry in the order was taken as proof it starts Linux; see 3.
8. A cut first journal write hung every later start. Each write now goes
   to a `.part` file and is renamed.
9. The run could exit into the installer's own screens. It now never
   returns: it restarts, or waits.
10. The window could leave the computer armed with no restart. It now
    checks the restart started and takes the arm back if not, or if the
    arm's answer was lost.

Also: a battery with no charger is refused (at the check, the arm and on
the stick), sleep and the lid switch are held off on the stick, a disk with
LVM or RAID holders counts as busy, and `sdaa` is no longer a partition of
`sda`. An abort before anything moved now puts the guard back and clears
the journal, so the computer is as it was. Not fixed, and owed: a drive
that returns other bytes after the move leaves the run stopped for good
with Linux kept from starting (it is the case the drive-health refusal is
there for); a computer converted with an older kit's stick cannot reclaim.

What the tests hold: the run cut at every one of its journal writes, and
each step failing once, all resume to the same bytes; a resume refuses a
table it did not leave; a plan made by `reclaim::plan` at the real 64 MiB
chunk, on a 140 MiB sparse disk file, passes the stick's checks and moves
every byte; a journal whose newer copy is torn falls back to the older
one, and two torn copies are a refusal, never "not started"; fourteen
stick-side refusals; the boot-file rules for six ESP states; the GRUB
block removal; the words. The guard and the finish themselves need root
and a real ESP, so they are held only by the rig.
